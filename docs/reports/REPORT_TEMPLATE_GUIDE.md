# 테스트 결과 보고서 작성 가이드

이 프로젝트에서 테스트 결과를 팀장 보고용 문서(.docx)로 정리할 때 따르는 표준 양식이다.
최신 예시: `docs/reports/CIMO_PoC_테스트결과_보고_20260705.docx` (2026-07-05, Day 1~7 종합)

## 왜 이 가이드가 필요한가

테스트를 진행할 때마다 매번 새로운 형식으로 보고서를 쓰면, ① 보는 사람이 매번 다른 구조에
적응해야 하고 ② 빠뜨리는 항목이 생기기 쉽다. 아래 구조를 그대로 따르면 이런 문제를 방지할 수 있다.

## 문서 구조 (본문 + 별첨)

**본문은 바쁜 관리자가 1~2분 안에 훑어볼 수 있도록 간략하게, 별첨은 궁금하면 더 볼 수 있도록 상세하게 작성한다.**

### 본문

1. **테스트 목표**
   - 통합(기능) 테스트 목표: 확인하려는 핵심 기능을 항목별로 나열
   - 성능 테스트 목표: 반드시 정량적 수치로 명시 (예: "초당 2,000건 처리", "±60초 이내 99% 이상")
   - "Day 1", "Day 7" 같은 진행 일정 구분은 본문에 넣지 않는다 (보고서는 결과 중심, 일정은 README.md/AM_ARCHITECTURE.md에만 기록)

2. **테스트 환경**
   - 사용한 PC/서버 사양을 표로 명시 (CPU, RAM, 역할)
   - 불필요한 부연 설명(변동성 안내 등)은 생략하고 사실만 표로 정리

3. **테스트 시나리오 및 케이스**
   - 맨 앞에 "통합(기능) 테스트: N개 시나리오·M개 케이스 / 성능 테스트: N개 시나리오·M개 케이스" 형태로 개수를 먼저 짧게 명시
   - 이후 각 시나리오는 표로: 확인한 상황(쉬운 말로, 여러 항목이면 줄바꿈으로 나열 — "/"로 이어붙이지 않음) + 결과만
   - 상세 목표·실측치·원인 설명은 여기 넣지 않고 별첨으로 뺀다

4. **종합 결론**
   - "PoC 목적 달성도": 이 PoC의 본래 목적을 기준으로 달성 여부를 평가
   - "실 환경 구축 방향": 실측으로 확인된 원인이 실 서버 환경에서는 어떻게 해소 가능한지 제시

### 별첨

- 시나리오/케이스별로 "쉬운 설명 → 목표/실측치 표 → 원인(쉬운 비유 포함)" 순서로 상세 기술
- 처음 보는 사람 기준으로 용어를 풀어 쓴다 (예: "RCS" → "카카오 리치메시지(RCS)")
- 발견·수정한 버그의 개별 나열은 넣지 않는다 (원인 설명에 필요한 만큼만 자연스럽게 녹여서 서술)

## 문체 규칙

- 서술문은 "~했다/~한다"가 아니라 "~함/~됨/~임"으로 끝나는 개조식으로 작성
- 예: "확인했다" → "확인함", "판단한다" → "판단함", "해소된다" → "해소됨"

## 형식·제작 규칙

- 파일 형식: `.docx` (Word). Claude가 작성할 경우 `/mnt/skills/public/docx/SKILL.md`의 docx-js(Node) 방식 사용
- 작성 후 반드시 PDF로 변환 + 렌더링하여 육안(또는 텍스트 추출)으로 확인 후 전달 (스킬 지침 준수)
- 저장 위치: `docs/reports/`
- 파일명 규칙: `CIMO_PoC_테스트결과_보고_YYYYMMDD.docx` (보고 시점 날짜를 붙여, 이전 보고서를 덮어쓰지 않고 이력으로 남긴다)
